# Mimir 0.5.0 — See Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make an agent's memory inspectable and correctable by a human: a memory browser with edit, delete and restore, the missing purge job for soft-deleted rows, project archiving, and a real 404 for unknown URLs.

**Architecture:** Services first, UI second, exactly as 0.1.0–0.4.0 did it. `lib/memory/service.ts` gains the deleted-row verbs; a pg-boss `purge` worker hard-deletes past the retention window; the browser is one server page under `/app/projects/[slug]` driven by `searchParams` (`path`, `q`, `deleted`) so every view is linkable and no client state is needed; mutations are server actions that audit one row and revalidate.

**Tech Stack:** Next.js 16 App Router, TypeScript strict, Tailwind v4 (theme aliases only), Postgres 18 + pgvector, pg-boss 12, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-25-mimir-design.md` (§8 memory model and soft delete, §9 retrieval, §17 UI, §19 audit). Read it alongside this plan; the spec wins when they disagree.

## Global Constraints

- Dynamic pages declare `export const instant = false`. Server actions live in `actions.ts` with `'use server'`; client forms live in their own `.tsx` with `useActionState`.
- Styling uses only `--bg`, `--bg-raised`, `--bg-sunken`, `--fg`, `--text-muted`, `--border`, `--accent`, `--accent-fg`, `--danger`. `styles/theme.test.ts` fails on any Tailwind palette class.
- Every mutation writes exactly one audit row with a namespaced action, `targetType`, `targetId`, and no memory body in `detail`.
- Access is enforced in the service via `requireProjectRole`, never in the page. A read grantee gets 403-shaped errors, not disabled controls alone.
- Memory paths are normalised by `normalisePath`; a browser URL is a *hint*, never trusted input.
- Retention is 30 days for soft-deleted memories (`PURGE_AFTER_DAYS = 30`).
- Tests: `npm test`, `npm run test:int` (needs `./scripts/test-db.sh up`), `npm run typecheck` bare.
- Version is `0.5.0`. Changelog entries go under `## [0.5.0] - 2026-10-26`.
- Deleted memories are recoverable until purge; nothing in this release may hard-delete a row that is inside its window.

## Review Focus

1. **Restoring a deleted memory never overwrites a live one.** If the path has been rewritten since deletion, the restore is refused with a message naming the conflict and the deleted row stays deleted.
2. **Purge deletes only what is past its window.** A memory deleted 29 days ago survives; one deleted 31 days ago goes; live rows and other projects are untouched, and the job reports how many it removed.
3. **The browser cannot leak across projects.** A stranger gets 404, a read grantee can look but not edit, and a path crafted in the URL (`../`, `/etc/passwd`, empty) resolves to a 404 rather than a 500.
4. **An edit never loses a memory when the model is down.** Saving succeeds while embeddings and extraction are failing, and the stale summary is cleared so the next extract rewrites it.
5. **Archiving is reversible and quiet.** An archived project leaves every list and every API response, its memories and grants survive, and restoring it needs no data migration.

### Task 1: Deleted-row verbs

**Files:**
- Modify: `lib/memory/service.ts`
- Test: `lib/memory/service.int.test.ts`

**Interfaces:**
- Consumes: `requireProjectRole`, `withUser`, `normalisePath`, `audit`.
- Produces:
  - `type DeletedMemory = { path: string; title: string; deletedAt: Date }`.
  - `listDeletedMemories(userId: string, projectId: string, limit = 100): Promise<DeletedMemory[]>` — requires `read`, newest deletion first.
  - `restoreMemory(userId: string, projectId: string, path: string): Promise<{ restored: true } | { restored: false; reason: 'not_found' | 'conflict' }>` — requires `write`; `conflict` when a live row already holds that path.
  - `purgeDeletedMemories(now?: Date): Promise<{ removed: number }>` — install-wide, `withAdmin`, deletes `deleted_at < now() - 30 days` only, so it can run as a job. Export `PURGE_AFTER_DAYS = 30`.

`restoreMemory` is one statement: `update memories set deleted_at = null where project_id = $1 and lower(path) = lower($2) and deleted_at is not null and not exists (select 1 from memories live where live.project_id = $1 and lower(live.path) = lower($2) and live.deleted_at is null) returning id`. Zero rows means either `not_found` or `conflict`; distinguish with one follow-up `select deleted_at from memories where ... order by deleted_at desc limit 1` (a live row ⇒ `conflict`).

**Interfaces:**
- Consumes: `getProject`, `treeMemory`, `readMemory`, `searchMemories`.
- Produces: the page contract `searchParams: Promise<{ path?: string; q?: string; deleted?: string }>`.

Layout: two columns on `lg` (320 px tree, flexible reader), stacked on mobile. The tree groups rows by directory from `treeMemory(user.id, project.id, '', 4)`; each entry is a `Link` to `?path=<path>` and is marked with a dot when `hasSummary`. The reader shows path as breadcrumbs, `title` (L0), `summary` (L1) in muted text when present, `body` (L2) in a `<pre>` that wraps, and the metadata line `kind · updated <ISO>`.

Behaviour:
- no `path` → show the tree and a "Choose a memory, or search" empty state.
- `path` given but `readMemory` returns null → `notFound()`.
- `q` given → render `searchMemories({... query: q, limit: 50})` results instead of the tree, each linking to its path with `?path=`.
- `deleted=1` → render `listDeletedMemories` instead of the tree (Task 5 fills in the actions).
- No project, or no access → `notFound()`; never a 403 page, so a stranger cannot tell a project exists.

### Task 4: Edit, delete and restore from the browser

**Files:**
- Create: `app/(product)/app/projects/[slug]/actions.ts`, `app/(product)/app/projects/[slug]/editor.tsx`, `app/(product)/app/projects/[slug]/danger.tsx`
- Modify: `app/(product)/app/projects/[slug]/page.tsx` (render the controls), `app/(product)/app/projects/[slug]/tree.tsx` (deleted view entry point)
- Test: `app/(product)/app/projects/browse-actions.test.tsx`

**Interfaces:**
- Consumes: `writeMemory`, `deleteMemory`, `restoreMemory`, `listDeletedMemories`, `requireProjectRole`.
- Produces: `saveMemoryAction(prev, formData)`, `deleteMemoryAction(prev, formData)`, `restoreMemoryAction(prev, formData)`, each `(prev: ActionState, formData: FormData) => Promise<ActionState>` with `ActionState = { ok?: string; error?: string }`.

Behaviour:
- `saveMemoryAction` reads `projectId`, `path`, `body`; calls `writeMemory({ userId, projectId, path, body, source: 'web' })`; audits `memory.write` with `{ via: 'web', path }`; returns `{ ok: 'Saved.' }` and revalidates the browser path. A rejected path or oversized body returns its message, never a 500.
- `deleteMemoryAction` audits `memory.delete` with `{ via: 'web', path }` and redirects to `?deleted=1`.
- `restoreMemoryAction` audits `memory.restore` and redirects to `?path=<path>`; a `conflict` result returns `{ error: 'A live memory already uses this path. Rename one of them first.' }`.
- Only `owner`/`write` see the editor and the delete button; a read grantee sees the body, no controls, and a line saying they have read access.

`editor.tsx` is the only client component: a `useActionState` form with a `<textarea>` for the body (monospace, 24 rows), Save, and the dirty-state hint "Saving clears the summary until the model rewrites it."

**Interfaces:**
- Consumes: nothing.
- Produces: a matcher that covers every path, and a rewrite to `/api/__missing` for a path that cannot be a page.

Background (verified in 0.4.0): Next 16 streams a dynamic route's shell before `notFound()` resolves, so an unknown `[locale]` or `[agent]` answers **200** with a not-found body. A path under `/api` with no route handler answers a real 404, so rewriting there restores the status.
