# Mimir 0.8.0 — Teams Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a group of people share projects without sharing passwords or copying grants one person at a time.

**Architecture:** A team is a named list of users with an owner. Sharing a project with a team is a normal `project_grants` row with `principal_type = 'team'` — the enum value the schema has reserved since 0.1.0 — so no existing grant, query or UI needs migrating. The work is three things: the two tables, the RLS predicates that teach "can I see this project" about team membership, and the screens to create a team and share with it.

**Tech Stack:** Postgres 18 (tables, RLS, `create or replace function`), Next.js 16 server components + server actions, the existing `lib/projects/access.ts` role model, Vitest against a real database.

**Spec:** `docs/superpowers/specs/2026-10-25-mimir-design.md` §7 (tenancy and access), §5 (`project_grants`), §17 (UI), §19 (audit). §23 lists Teams as the last deferred item.

## Global Constraints

- A team grants **project access, never ownership**. Ownership stays `projects.owner_user_id`; no team member may archive, delete, re-share or change settings of a team-shared project.
- Access is evaluated on every request from the database. Removing a member or a grant takes effect immediately, with no session or cache to invalidate.
- RLS is the enforcement, not a `where` clause the caller might forget: the team branch belongs inside `can_access_project` / `can_write_project`, so memories, versions, grants and search inherit it for free.
- One audit row per mutation, namespaced: `team.create`, `team.delete`, `team.member_add`, `team.member_remove`, `project.grant`, `project.revoke`. Never an email in `detail`.
- A grant may only name a team the granter belongs to, so nobody can attach a stranger's team to their project.
- `slugify` is shared, not copied: it moves out of `lib/projects/service.ts` into `lib/slug.ts` and both callers import it.
- Release is `0.8.0`: MINOR, additive.

## Review Focus

1. **Removing someone ends their access at once.** Remove a member from a team that holds a write grant; their very next request is refused, with no re-login.
2. **A team is not an owner.** A team member with a write grant cannot archive the project, delete it, change its learning settings, or add another grantee — each answers `forbidden`, not a silent no-op.
3. **Deleting a team revokes what it shared.** Its `project_grants` rows are gone, and a former member's next request to that project is refused.
4. **Two teams do not stack into ownership.** A user in a read team and a write team gets `write`; nothing about teams can produce `owner`.
5. **A stranger sees nothing.** A user who is in neither team and holds no grant gets the not-found answer from the UI and `forbidden` from the API, including via `search`, `digest` and `versions`.

### Task 1: The tables and the policy that reads them

**Files:**
- Create: `lib/db/migrations/0006_teams.sql`
- Test: `lib/db/migrations/teams.int.test.ts`

**Interfaces:**
- Produces: tables `teams(id, owner_user_id, name, slug, created_at, updated_at)` with `unique (owner_user_id, slug)` and `team_members(team_id, user_id, role, created_at)` with `primary key (team_id, user_id)`, `role text not null default 'member' check (role in ('owner','member'))` and an index on `user_id`. Functions `is_team_member(p_team uuid)`, `owns_team(p_team uuid)`, and **replaced** `can_access_project(p_project uuid)` / `can_write_project(p_project uuid)` that also match `project_grants` rows whose `principal_type = 'team'` and whose team has the caller in `team_members`.

**RLS on the new tables**, written like `0002_security.sql` (ENABLE, not FORCE; predicates in `SECURITY DEFINER` helpers with `search_path = public, pg_temp`):
- `teams`: SELECT when `owner_user_id = app_user_id() OR is_team_member(id)`; INSERT `WITH CHECK (owner_user_id = app_user_id())`; UPDATE and DELETE only when `owner_user_id = app_user_id()`.
- `team_members`: SELECT when `is_team_member(team_id) OR owns_team(team_id)`; INSERT and DELETE when `owns_team(team_id)`; no UPDATE policy (a member is added or removed, not edited).
- GRANTs to `mimir_app`: SELECT/INSERT/UPDATE/DELETE on both.
- `create trigger teams_updated_at before update on teams for each row execute function set_updated_at()`.

Team grants are deleted by the service (Task 3), not by a foreign key: `project_grants.principal_id` is polymorphic and has no FK by design.

- Produces `lib/teams/service.ts`:
  - `type TeamRole = 'owner' | 'member'`
  - `type TeamSummary = { id: string; slug: string; name: string; role: TeamRole; memberCount: number }`
  - `type TeamMember = { userId: string; email: string; name: string; role: TeamRole }`
  - `createTeam(userId: string, name: string): Promise<TeamSummary>` — slug from `slugify(name)`, retrying `-2`…`-5` on `(owner_user_id, slug)` conflict; inserts `team_members` with role `owner` in the same transaction.
  - `listTeams(userId: string): Promise<TeamSummary[]>`
  - `getTeam(userId: string, slug: string): Promise<{ team: TeamSummary; members: TeamMember[] } | null>`
  - `addTeamMember(actorId: string, teamId: string, email: string): Promise<TeamMember>` — unknown or non-active user → `invalid_params` "no active user with that email"; already a member → `invalid_params` "already in this team".
  - `removeTeamMember(actorId: string, teamId: string, userId: string): Promise<void>` — refuses to remove the last owner (`invalid_params` "a team needs an owner").
  - `deleteTeam(actorId: string, teamId: string): Promise<void>` — deletes the team (members cascade) **and** its `project_grants` rows in the same `withUser` transaction.
  - Errors are `Error & { code: 'forbidden' | 'invalid_params' | 'not_found' }` like `lib/users/service.ts`; every mutation requires the actor to hold `owner` in that team and writes one audit row.

### Task 3: Grants that can name a team

**Files:**
- Modify: `lib/projects/access.ts`, `lib/projects/service.ts` (`listProjects`)
- Test: `lib/projects/access.int.test.ts`, `lib/projects/service.int.test.ts`

**Interfaces:**
- Produces in `lib/projects/access.ts`:
  - `type PrincipalType = 'user' | 'team'`
  - `grantProject(actorUserId, projectId, principalType: PrincipalType, principalId: string, role: 'read' | 'write'): Promise<void>` — requires `owner` on the project, and for `'team'` also requires the actor to be a member of that team (`forbidden` otherwise) and the team to exist (`not_found`).
  - `revokeGrant(actorUserId, projectId, principalType, principalId): Promise<void>` — same guards.
  - `listGrants(actorUserId, projectId): Promise<GrantRow[]>` where `GrantRow = { principalType: PrincipalType; principalId: string; label: string; role: 'read' | 'write' }` and `label` is the email for a user and the team name for a team.
  - `projectRole` gains the team branch and returns the **best** role: owner (row owner) beats a `write` grant from any source, which beats `read`.
- Produces in `lib/projects/service.ts`: `listProjects` includes projects shared with a team the user belongs to, with the role the team grant gives.

`projectRole` must keep its existing shape — one `withUser` query returning `owner_user_id` plus the best grant role — and gain a join rather than a second round trip:

```sql
select p.owner_user_id,
       (select max(case g.role when 'write' then 2 else 1 end)
          from project_grants g
          left join team_members m
            on g.principal_type = 'team' and m.team_id = g.principal_id and m.user_id = $2
         where g.project_id = p.id
           and (g.principal_id = $2 and g.principal_type = 'user' or m.user_id is not null)) as rank
```

mapped back to `'write' | 'read' | null`.
